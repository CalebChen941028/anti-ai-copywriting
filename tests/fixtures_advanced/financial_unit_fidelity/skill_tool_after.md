# 核心清算系统去O与微服务改造成效通报

本次改造历时9个月，覆盖核心系统12个微服务模块。四项生产实测指标全部达标，另有一项年度经常性支出被压减。下表数据取自生产环境，不是压测推算，也不是理论值。

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 数据库峰值查询时延 | 850 ms | 180 ms |
| P99 长尾时延 | 2.4 s | 420 ms |
| 集群峰值吞吐 | 1.2 万笔/秒 | 4.8 万笔/秒 |
| 机房级故障自动切换恢复 | 15 分钟 | 30 秒以内 |

## 指标读法

**时延。** P99 指最慢的那一小部分请求的耗时上限，比平均值更能说明系统在压力下的真实表现。改造后，平均值与长尾时延同时下移。

**吞吐。** 集群峰值处理能力较改造前提升，容量由集群整体承担。

**可用性。** 机房级故障的自动切换恢复时间，从以分钟计降到以秒计。这是清算业务连续性方案里最关键的一项参数，直接决定单机房失效时业务能否继续运行。

**成本。** 节约的 3,000 万元来自冷热数据分层归档与 NVMe 存储池化两项措施。这笔节约是年度支出减少，不是一次性收益，会在后续每个财年体现。

## 口径说明与待补事项

建议补齐以下几项信息后再对外发布：

- 【待补：预算节约额的计算口径，是否含折旧摊销、机房电力与人力成本】
- 【待补：峰值吞吐对应的是压测场景还是生产峰值，日终批量与日间峰值是否叠加】
- 【待补：秒级切换的验证方式与演练样本量】
- 【待补：改造期内的计划内停机时长与回退次数】

如果通报要面向董事会，建议同时给出改造前后的可用性统计和故障工单数量。这两项比时延数字更容易被非技术背景的决策者引用。
